# نقل الباك-إند بالكامل إلى Supabase الخاص بك (Coolify)

## ما تم التحقق منه الآن

- السيرفر الجديد `https://supamecha.hub4tech.net` شغّال وواصل: REST و Auth و Storage كلها ترد.
- مفتاح `service_role` الذي أعطيته يعمل ويعطي صلاحية إدارية كاملة.
- السيرفر الجديد **فارغ تماماً**: لا مستخدمين (`auth/admin/users` = 0)، ولا buckets، ولا جداول للمشروع.
- المصدر الحالي فيه: 40+ جدول في `public`، مخطط `private` مع دوال الصلاحيات، دوال وتريجرات (نقاط، إشعارات، سجل نشاط، استعادة نسخة)، امتداد `citext`، و5 buckets: `backups`, `expense-receipts`, `invoices`, `member-reports`, `note-attachments`.

## مطلوب منك قبل التنفيذ (شغلتين فقط)

1. **مفتاح anon / publishable** للسيرفر الجديد — الواجهة (المتصفح) لا تستعمل service_role أبداً.
2. **رابط قاعدة البيانات المباشر** (`postgresql://postgres:...@host:5432/postgres`) للسيرفر الجديد.
   ضروري لأن: إنشاء الجداول والدوال والسياسات، ونقل مستخدمي `auth.users` بكلمات مرورهم المشفّرة، لا يمكن عملهما عبر الـAPI — فقط عبر اتصال Postgres مباشر.
   إذا Postgres غير مفتوح للخارج على Coolify، افتح المنفذ مؤقتاً أثناء النقل ثم أغلقه.

## خطوات النقل

1. **البنية**: أخذ نسخة بنيوية من المصدر (`public` + `private` + الامتدادات + الأنواع + الدوال + التريجرات + سياسات RLS + الـGRANTs) وتطبيقها على القاعدة الجديدة.
2. **المستخدمين**: نقل صفوف `auth.users` و`auth.identities` كما هي — كلمات المرور تبقى نفسها لأن الهاش ينتقل معها. يتم تعطيل تريجر `on_auth_user_created` أثناء النقل حتى لا يعيد إنشاء الملفات الشخصية.
3. **البيانات**: نقل كل صفوف جداول `public` بالترتيب (الأب قبل الابن) مع تعطيل التريجرات، حتى لا تُحتسب نقاط أو تُرسل إشعارات وهمية أثناء النقل. البيانات المالية تنتقل مشفّرة كما هي، وتبقى تُفتح بنفس كلمة الخزنة عندك.
4. **الملفات**: إنشاء الـ5 buckets بنفس الإعدادات (كلها خاصة) وتنزيل كل ملف من القديم ورفعه للجديد بنفس المسار، ثم مطابقة العدد بين الطرفين.
5. **الأسرار والوظائف الخادمية**: `LOVABLE_API_KEY` وباقي المفاتيح تُضبط كمتغيّرات بيئة على حاوية التطبيق في Coolify. جدولة النسخ الاحتياطية (كل 10 أيام) تُعاد على القاعدة الجديدة.
6. **توجيه التطبيق**: تحديث `Dockerfile` / `docker-compose.yml` ليشير البناء على الـVPS إلى `https://supamecha.hub4tech.net` بالمفتاح العام الجديد، ثم إعادة البناء.
7. **التحقق**: مقارنة عدد الصفوف لكل جدول بين القديم والجديد، عدد المستخدمين، عدد ملفات كل bucket، ثم تسجيل دخول فعلي بحساب واحد على النسخة الجديدة، وفتح الخزنة المالية للتأكد من فك التشفير.

## ملاحظة مهمة حول نسخة Lovable

المعاينة داخل Lovable مربوطة إجبارياً بباك-إند Lovable Cloud ولا يمكن توجيهها لسيرفرك. لذلك بعد النقل:
- **النسخة الحيّة على الـVPS** = السيرفر الجديد (هي التي يستخدمها فريقك).
- **المعاينة داخل Lovable** = تبقى على الباك-إند القديم للتطوير فقط.
أي تعديل مستقبلي على البنية يجب تطبيقه على الاثنين (سأعمل ملف SQL مرافق لكل تعديل لتشغيله على سيرفرك).

## تفاصيل تقنية

- الأدوات: `pg_dump --schema-only --no-owner --no-privileges` للبنية، `pg_dump --data-only --disable-triggers` للبيانات، و`COPY` عبر `psql` للنقل.
- امتداد `citext` و`pgcrypto` و`uuid-ossp` تُنشأ أولاً قبل تطبيق البنية.
- `SET session_replication_role = replica` أثناء إدخال البيانات لتفادي التريجرات والقيود المرجعية، ثم إرجاعها.
- الملفات تُنقل عبر Storage API (تنزيل موقّع من القديم → رفع بـservice_role للجديد) بدفعات متوازية مع إعادة محاولة عند الفشل.
- لا يُكتب أي مفتاح `service_role` داخل كود الواجهة؛ فقط `anon` في متغيّرات البناء.
